# リリース運用

## 公開前

既定ブランチは `develop`、公開ブランチは `main` とします。リポジトリはユーザーの最終承認と初回リリース生成の確認まで非公開を維持します。既定ブランチの変更にはリポジトリの管理権限が必要です。

各IssueのPRをdevelopへ統合し、ユーザーの通しプレイと修正後の再確認を終えます。対象件数と完了率、実機確認結果、既知の制限、候補ZIPのSHA-256、developからmainへの公開PRを報告します。承認前にmainへ統合しません。

公開前には全ブランチのファイルに加え、Issue・PR本文、Actionsのログと成果物も確認します。原文、ゲーム資産、個人パス、実機ログ、認証情報を公開対象に含めません。通しプレイの記録は公開可能な確認結果だけを残します。

## バージョンと自動処理

初回の `VERSION` は `1.0.0` です。翻訳修正はpatch、対応範囲の追加はminor、導入互換性の変更はmajorを上げます。同じ版の成果物を後から差し替えません。

承認後、developからmainへマージコミットで統合します。正式リリースのActionsは次の順序で動きます。

1. Windowsで導入時生成ツールをビルドし、依存ライセンスとともに検証ジョブへ渡す。Windows・Linuxで公開基準、翻訳、テスト、正式ビルド、再現性、配布ZIPを検査する。
2. 同じ生成ツール成果物を用いてLinuxで正式成果物を再生成し、未訳・要確認・対象範囲未判定・試作版の混入を拒否する。Windows・Linuxの検証済み成果物と再生成結果のSHA-256も照合する。
3. `v<VERSION>` のドラフトReleaseを対象コミットSHA付きで作成する。
4. ZIPとSHA-256ファイルをアップロードし、ダウンロードし直して一致を確認する。
5. 一致したドラフトをReleaseへ変更する。

失敗時はReleaseを公開状態へ進めません。タグの参照先が異なる場合は停止します。再実行では既存ドラフトを再利用し、公開済みReleaseは成果物を検証するだけで変更しません。作成にはActionsの `contents: write` を使い、独自トークンをリポジトリへ保存しません。

チェンジログは[GitHubの自動生成](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)を使います。PRに「翻訳」「導入」「開発基盤」「文書」のラベルを付け、`.github/release.yml` の分類に反映します。

初回は非公開リポジトリ内で生成に成功したことを確認してから、承認済みの内容でリポジトリを公開します。承認後に配布内容が変わった場合は再検証と再承認が必要です。

## 検証の限界

PRのCIは原本不要の正式ビルドとWindowsの導入テストを実行し、Windows・Linux間でもZIPがバイト単位で一致することを検査します。成果物は7日間保管します。ZIPには既存の `LICENSE` を内容を変更せず同梱し、導入前の整合性検査の対象にも含めます。

リリース作成の失敗・再試行・重複防止は自作のGitHub応答によるテストで検証します。実際の正式Release作成はmain統合時まで実行しません。
